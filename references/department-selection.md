# 部门设定与选题

## 两种入口

有 JD：区分明确职责与未知信息。足够具体时直接用；只有“熟悉大模型、Agent、有工程能力”时保留这些要求，补充一个模拟部门场景。不得把补充内容宣称为该公司的事实。

无 JD：用户可指定 RAG、Agent 平台、客户应用、后训练等方向；也可让模型选择。方向之内仍须说明交付物、使用者、当前困难、约束与实习/初级成员的工作范围。

不要只把简历里的技术词拼成部门需求。先独立设定可信的业务问题，再映射简历，最后校准岗位级别和经历相关性。目标业务可以新，但应留有候选人可凭既有经验推理的入口。

## 生成部门背景

用 2–4 句话交代：团队为谁交付什么，现在哪里做不好，有什么关键约束，岗位会参与什么。不需要虚构精确用户量、营收、团队人数或生产故障史。

业务困难可以来自错误代价、人工协作、数据更新、需求变化、反馈歧义、运行可靠性、实验可信度或成本限制。按真实场景选两三个，不能每场全选。

然后推导 3–4 项本场重点能力，每项必须对应一个部门困难。再找简历入口，并检查其相关性、证据价值与互补性。不要将同一能力在三个项目里重复确认占据全场。

内部检查：去掉公司和行业名之后，考察布局是否与上一场几乎一样？若是，检查有没有真正使用新部门目标与约束。基础问题允许重叠，不强求为了新颖而出偏题。

## 示例 A：商品内容生产（展示推导方式，不是固定题库）

背景：电商 SaaS 团队根据商品表格和商家资料生成标题、卖点与详情文案，运营审核后发布。当前文案流畅但偶尔混淆 SKU 参数，各渠道要求也不同，人工修改量仍大。希望在一个品类中验证能否减少审核与修改工作，实习生参与数据整理、生成流程和评测。

| 工作困难 | 想确认的能力 | 可寻找的经历入口 |
|---|---|---|
| 文案通顺却可能写错商品事实 | 区分可生成表达与必须受源数据约束的事实 | 问数约束、商品规格匹配、工具结果处理 |
| 好文案不只有一个标准答案 | 把质量要求变成可执行的验证 | Rubric、硬检查、人工或模型评审 |
| 运营修改混合了纠错、渠道要求和个人偏好 | 理解反馈含义与训练标签质量 | 数据清洗、轨迹筛选、SFT 数据 |
| 多渠道变更导致反复改逻辑 | 识别稳定接口与业务差异 | 工具标准化、模块化、配置管理 |
| 团队考虑增加 Agent 或微调 | 根据问题定位选择投入 | 多 Agent 取舍、无收益实验复盘 |

可先问经历中的评测分工，再迁移到“运营重写了事实正确的文案，是否算失败”。若已经能区分反馈原因，并说明如何记录，就可转题，不必沿标注一致性、统计检验一路问到头。

## 示例 B：Agent 运行平台

背景：团队为内部业务提供 Agent 运行服务，需要接入不同工具，并让使用者看到长任务的实际进度。当前工具配置变化和任务执行状态会影响其他模块，岗位参与服务接入与运行链路维护。

业务困难可引出调用契约、运行资源、状态生命周期和定位问题的能力。可从工具服务化或协作运行时进入，具体框架追问依回答确认。不能规定该方向必考 FastAPI 依赖注入或 SSE。

## 示例 C：小模型任务能力改进

背景：团队研究小模型执行多轮业务任务的能力，已有可交互的工具环境。当前难以区分提升来自训练、数据筛选还是环境变化，采集和评测资源有限。岗位参与数据、rollout 环境或实验验证。

业务困难可引出环境与模型错误的区分、轨迹可用性、实验可比较性和投入判断。可从训练项目进入，也可利用实习中的评测或运行优化经验。不要因算法方向就默认必须追问完整优化器或分布式训练源码。

## 历次面经提供的观察

以下是提问的观测与可迁移机制，不是对公司政策或面试官个人经历的事实判断。

- 工具服务化后追问 FastAPI 依赖注入：说明抽象架构中的资源获取和生命周期可以成为具体入口。未使用该机制时理解替代实现。
- 关闭页面一段时间后恢复进度：通过时间变化观察页面、连接和任务的状态关系。不能只看是否说出 SSE。
- 实际数据库接入、接口、鉴权与重构：检查模型输出到真实操作之间的边界。先确认真实实现范围。
- BM25、多路召回与正确性：观察技术选择是否对应业务效果，而非组件越多越好。
- 实习收获和技术亮点：观察候选人能否选出有意义的设计并形成自己的理解，不能等同要求其独立负责生产架构。
- GRPO 数据和轨迹是什么样：将抽象概念落实到一次可描述的数据/执行实例，随后按岗位价值决定继续还是转题。

这些案例用于学习问题产生的方法。不要把它们全部安排进每一场，也不要把候选人过去某题没答出来当成本场必考理由。
